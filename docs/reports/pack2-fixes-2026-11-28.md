## Per-Item Changes, Mechanisms & Evidence

### Item 1 (M5) — Validate `received_by` in DB & Align `edit_daily_entry()`
- **Mechanism:**
  - Created shared `BEFORE INSERT OR UPDATE` trigger function `public.guard_received_by()` (`SECURITY DEFINER`, `set search_path = public`, `EXECUTE` revoked from `public, anon, authenticated`), attached to `public.daily_entries` (`entries_guard_received_by`) and `public.agent_payments` (`payments_guard_received_by`).
  - `NULL` stays allowed everywhere (`CloseoutPage.tsx:246-251`, legacy `offlineQueue.ts` payloads, `coalesce(received_by, created_by)` fallback).
  - On `UPDATE`, unchanged `received_by` (`new.received_by is not distinct from old.received_by`) passes without re-validation.
  - On new/changed non-null `received_by`, verifies `profiles.active = true` AND eligible role in `('owner', 'manager', 'co_owner', 'staff')` checking **both** `profiles.role` and `user_roles.role` (matching `staff_directory()`). Owner stays allowed. Error code: `invalid_receiver`.
  - **Midday-deactivated receiver edge case:** In `guard_received_by()`, on `agent_payments` `INSERT` with `source_entry_id IS NOT NULL` (read via `to_jsonb(new) ->> 'source_entry_id'` so the shared trigger compiles cleanly on `daily_entries`), allows the insert when `new.received_by` equals the parent `daily_entries` row's `coalesce(received_by, created_by)`. Inside `edit_daily_entry()`, validates `v_receiver` with the exact same `invalid_receiver` rule only when `p_received_by` changes the effective receiver (`p_received_by is distinct from coalesce(v_entry.received_by, v_entry.created_by)`), and preserves `NULL` when `p_received_by` is omitted on a `NULL` row.
- **Test evidence (`25_pack2_receiver_deactivated.sql` Section 1):**
  - Proves `INSERT` fails (`invalid_receiver`) for inactive staff, agent profile, and unknown UUID on both `daily_entries` and `agent_payments`.
  - Proves `UPDATE` and `edit_daily_entry()` fail (`invalid_receiver`) when changing `received_by` to inactive/agent/unknown.
  - Proves valid inserts succeed for active staff, Owner, multi-role `agent + staff`, and `NULL` (`CloseoutPage` style).
  - Proves midday-deactivated receiver edge case: Staff B receives cash + linked payment → Owner deactivates Staff B → OM runs `edit_daily_entry()` changing qty/cash (triggering `DELETE + INSERT` of both `old_debt` and `regular` linked payments) with Staff B unchanged → **succeeds** (`to_old = 650, advance = 50`); switching receiver to another inactive user → **fails** (`invalid_receiver`).
- **Pre-existing invalid `received_by` count (read-only):**
  - **Live database:** **UNVERIFIED** (builder VM has no live Supabase access, per `AGENTS.md`). Fixture baseline count: `0`.
  - Exact read-only SQL query for reviewer/owner to run against live DB (does not modify data):
    ```sql
    with bad_profiles as (
      select p.id from public.profiles p
       where not p.active
          or not (
               p.role in ('owner', 'manager', 'co_owner', 'staff')
               or exists (
                 select 1 from public.user_roles ur
                  where ur.profile_id = p.id
                    and ur.role in ('owner', 'manager', 'co_owner', 'staff')
               )
             )
    )
    select 'daily_entries' as tbl, count(*) as invalid_count
      from public.daily_entries e
     where e.received_by is not null
       and (e.received_by in (select id from bad_profiles)
            or not exists (select 1 from public.profiles p where p.id = e.received_by))
    union all
    select 'agent_payments' as tbl, count(*) as invalid_count
      from public.agent_payments ap
     where ap.received_by is not null
       and (ap.received_by in (select id from bad_profiles)
            or not exists (select 1 from public.profiles p where p.id = ap.received_by));
    ```

When `new.received_by is not null and new.created_by is not null and new.received_by <> new.created_by`, both OM and agent notifications show `မှတ်တမ်းတင်သူ <typist> · လက်ခံသူ <receiver>` (across delivery, bottle-only, and payment notices). ### Item 4 (D3) — Gate `staff_directory()`
- **Mechanism:** Replaced `public.staff_directory()` (`SECURITY DEFINER`, `set search_path = public`, `REVOKE ALL ... FROM PUBLIC, anon; GRANT EXECUTE ... TO authenticated`).
  - Caller must have an active profile (`42501` error for deactivated/null callers).
  - `is_staff_plus()` callers (including dual-role `staff + agent`) receive the full non-agent roster.
  - Pure agents (`not is_staff_plus()`) see ONLY non-agent profiles referenced via `coalesce(received_by, created_by)` across their own `daily_entries` and `agent_payments` for `app_agent_id()`.
- **Test evidence:** `25_pack2_receiver_deactivated.sql` Section 3 tests deactivated caller (`42501`), pure agent narrowing (including `created_by` fallback when `received_by IS NULL`), and dual-role `staff + agent` keeping the full roster.

### Item 5 (D4a) — `AuthContext` Deactivated Sign-Out & Race Guard
- **Mechanism:**
  - Extracted pure decision helpers `resolveRestoredProfile()` and `resolveSignInProfile()` in `src/lib/profileFetch.ts` with 7 new unit tests in `tests/unit/profileFetch.test.ts`.
  - In `src/context/AuthContext.tsx`:
    - `loadProfile()` (used by `getSession()` on session restore and non-signIn auth events) checks `resolveRestoredProfile()`; if `sign_out_inactive`, calls `await supabase.auth.signOut()` and clears auth state immediately.
    - Added `signingInRef` so `onAuthStateChange('SIGNED_IN')` does not call `setSession()` while `signIn()` is still verifying `profiles.active`. `LoginPage` therefore never unmounts prematurely on a deactivated sign-in and reliably displays `"ဒီအကောင့် ပိတ်ထားပါတယ် — ပိုင်ရှင်ကို ဆက်သွယ်ပါ"`.
- **Manual browser verification steps (for QA on live/staging):**
  1. Sign in as a deactivated staff account → confirm `LoginPage` stays mounted and displays `"ဒီအကောင့် ပိတ်ထားပါတယ် — ပိုင်ရှင်ကို ဆက်သွယ်ပါ"`.
  2. Sign in as an active staff account in Tab A; in Tab B (Owner), deactivate that staff account; refresh Tab A → confirm Tab A immediately signs out and returns to `LoginPage` without rendering the app shell.
  3. Sign in and refresh as active owner, manager, staff, and agent → confirm normal session restore.
