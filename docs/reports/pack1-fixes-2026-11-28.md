## Per-Item Changes & Mechanisms Chosen

### Item 1 (M2) — Remove `agent_id -> NULL` Bypass & Add `agent_immutable` Triggers
- **Mechanism chosen:**
  1. Replaced `public.guard_same_day_edit()` and `public.guard_month_lock()` (keeping `set search_path = public` and `revoke all ... from public, anon, authenticated`) with the legacy `old.agent_id is not null and new.agent_id is null` early-return bypass **removed completely**.
  2. Reused `0048`'s generic `public.guard_entry_agent_immutable()` (`if new.agent_id is distinct from old.agent_id then raise exception 'agent_immutable: ...'`) by attaching `BEFORE UPDATE` triggers `payments_agent_immutable` on `public.agent_payments` and `inventory_agent_immutable` on `public.inventory_movements`. Because `NULL is distinct from NULL` is `false`, pre-existing historical NULL rows still allow unrelated updates when `agent_id` stays `NULL`.
- **Proven in `24_pack1_staff_holes.sql`:** Staff & Owner nulling `agent_id` on yesterday's or locked-month `agent_payments`, staff switching `agent_id` on same-day `agent_payments`, and Owner changing/nulling `agent_id` on `inventory_movements` all fail (`agent_immutable`); additionally, behavioral tests on `write_offs` (which has no `agent_immutable` trigger) prove `guard_same_day_edit()` itself raises `same_day_only` and `guard_month_lock()` itself raises `month_locked` when `agent_id` is nulled.

### Item 2 (M1+M4) — Immutable Money/Date Columns, Positive Amounts, Linked-Payment Guard, Credit-Limit Delete Guard
- **`daily_entries` (`entries_before_write()`):**
  - **Mechanism chosen: REJECT** (rather than silently coerce) any `UPDATE` that changes `unit_price` (`unit_price_immutable`), `entry_date` (`entry_date_immutable`), or `created_at` (`created_at_immutable`). Rejecting ensures direct tampering attempts fail loudly with an error instead of returning HTTP 200. Neither `edit_daily_entry()` nor the UI's `change_reason` stamp modifies those columns.
- **`agent_payments` (`payments_before_write()`, `BEFORE INSERT OR UPDATE`, `SECURITY INVOKER`):**
  - Enforces `amount > 0` (`invalid_amount`) on both `INSERT` and `UPDATE`.
  - Rejects `UPDATE` changes to `payment_date` (`payment_date_immutable`), `created_at` (`created_at_immutable`), and `source_entry_id` (`source_entry_immutable`) — alongside `payments_agent_immutable` for `agent_id`.
  - **Linked payments on direct `UPDATE`:** Because `payments_before_write()` is `SECURITY INVOKER`, direct client calls execute with `current_user = 'authenticated'` (or `'anon'`), whereas `edit_daily_entry()` (`SECURITY DEFINER`) executes as its owner role (`postgres`). Rejecting `old.source_entry_id is not null and current_user in ('authenticated', 'anon')` (`linked_payment_immutable`) blocks all direct client updates to entry-linked payments while keeping `edit_daily_entry()`'s in-place receiver update working.
  - **Credit-limit shrink parity on direct `UPDATE`:** Also rejects direct non-OM `UPDATE` reducing `amount` (`new.amount < old.amount`) if `agent_outstanding(old.agent_id) + (old.amount - new.amount) > credit_limit`, closing the shrink-instead-of-delete variant of the credit-limit bypass.
- **`agent_payments` (`payments_before_delete()`, `BEFORE DELETE`, `SECURITY INVOKER`):**
  - **Linked payments on direct `DELETE`:** Rejects `old.source_entry_id is not null and current_user in ('authenticated', 'anon')` (`linked_payment_immutable`). Both `edit_daily_entry()` (`SECURITY DEFINER`) and PostgreSQL's `ON DELETE CASCADE` RI trigger (when deleting the parent `daily_entries` row) execute as the owner role rather than `'authenticated'`, so both legitimate paths continue working unchanged.
  - **Credit-limit delete bypass:** On direct non-OM `DELETE` (`current_user in ('authenticated', 'anon') and not is_owner_manager()`), checks `agents.credit_limit`; if `credit_limit > 0` and `agent_outstanding(old.agent_id) + old.amount > credit_limit`, rejects with `credit_limit`. OM callers are exempt.

### Item 3 (M6) — Reject `agent_id IS NULL` Inserts & Closed/Archived Agent Payment Inserts
- **`daily_entries` (`entries_before_write()`):** On `INSERT`, `new.agent_id is null` raises `agent_required`. On `UPDATE`, pre-existing historical NULL rows still pass unrelated updates (after enforcing the immutability checks and recomputing `amount = delivered_qty * unit_price`).
- **`agent_payments` (`payments_before_write()`):** On `INSERT`, rejects `new.agent_id is null` (`agent_required`), missing agent (`agent_not_found`), `closed_at is not null` (`agent_closed`), and `archived_at is not null` (`agent_archived`). Pre-existing historical NULL rows remain readable and allow unrelated same-day updates.

### Item 4 (M3/D2) — Inventory Lockdown
- Replaced all four `inventory_movements` RLS policies (`0002_rls.sql`):
  - `inventory_select`: `is_owner_manager() or agent_id = app_agent_id()`
  - `inventory_insert`, `inventory_update`, `inventory_delete`: `is_owner_manager()` only.
- Replaced `public.inventory_totals()` (`0023_agent_stats_inventory_rpc.sql`): changed caller gate from `public.is_staff_plus()` to `public.is_owner_manager()` (keeping `revoke all ... from public, anon; grant execute ... to authenticated;`).

### Item 5 (D1) — `agent_detail_stats(uuid)` Lockdown
- Replaced `public.agent_detail_stats(p_agent uuid)` (`0023_agent_stats_inventory_rpc.sql`): changed caller gate from `is_staff_plus() or exists(...)` to:
  ```sql
  if not (
    public.is_owner_manager()
    or (p_agent is not null and p_agent is not distinct from public.app_agent_id())
  ) then
  ```
  Using `p_agent is not null and p_agent is not distinct from public.app_agent_id()` avoids SQL three-valued `NULL` logic (where `false or (p_agent = NULL)` evaluates to `UNKNOWN`, causing `if not (UNKNOWN)` to skip raising!). Preserves `revoke all ... from public, anon; grant execute ... to authenticated;`.
